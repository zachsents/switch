# Standards

Every app in the suite follows these. Where possible the kit (`crates/kit`) enforces a rule in code, so breaking it fails a build or a debug assertion instead of waiting for review.

## Principles

The suite is simple, minimal and modern, and AI is woven through it so well it stops being noticeable. Together the apps should feel like an operating system built for working alongside AI.

- **Anything a person can do, an agent can do.** Every command and every piece of what's on screen (which image is shown, how far it's zoomed, which panel is open) can be driven by an agent. When an agent shows or changes something, it happens live: the window comes forward so the person sees it, without taking the keyboard.
- **Say it however you'd say it.** Fields that take a value, like a size, a length of time or a time of day, take plain words. A local parser reads the common forms instantly. Anything it can't read goes to the suite's fast decision model (`ai::decide`), which answers in about a second, and the field shows what it understood. Without a key, the parser still works. Look for more places where typing what you mean beats a row of controls, and prefer them.
- **Shared things are set once, for the whole suite.** API keys and anything like them aren't an app's business: an app finds them (`ai::keys`) and never shows them, asks for them or explains where they came from.

## Look

- **Color:** only `kit::Theme`. Backgrounds are pure black (dark) or pure white (light), every gray is a true neutral, and there are no accent colors or branding. The theme follows the system appearance.
- **Type:** the platform UI font (SF Pro on macOS), 13px body and 11px small. Numbers that change use tabular digits (`tabular_nums()`) so they don't shift.
- **Icons:** [Phosphor](https://phosphoricons.com), bold weight, drawn at 16px. MIT licensed, so the SVGs ship in the repo (`crates/kit/assets/icons`, with Phosphor's `LICENSE`). Add icons from the same package version (`@phosphor-icons/core` 2.1.1), bold weight only, so every icon matches.
- **Buttons are physical objects.** Each has a nearly flat face, a bevel around its edges (a crisp lit edge and a softer lit band along the top and left, the same in shade along the bottom and right), and a short ledge of shadow that stands it off the surface. Pressed, it sinks in: the bevel turns over, shading the top inside edge, a lip of light shows below, and the label drops 1px. Shortcut hints are drawn as small keys with the same bevel, one cap per key: ⌘ Enter is two keys side by side and ⌥⌘1 is three. Named keys are written the way macOS writes them: Enter, Space, Tab, Esc, ⌫, ⌦ and the arrows. Everything else (backgrounds, lists, text) stays flat, so the controls are what reads as touchable. *(Enforced: the look lives in `kit::Button`, `kit::Segmented` and `Theme::button*`. Apps can't restyle buttons.)*
- **Feedback for every input.** A button shows pressed whether it was clicked or its shortcut was used. *(Provided by `kit::main`.)*
- **A few choices are joined buttons.** Picking one of two or three options uses `kit::Segmented`: the chosen option stays pressed in, and each option is its own action with its own shortcut. More options than that are a `kit::Grid`.
- **Density:** compact. Controls and list rows are 28px tall.
- **Windows:** the titlebar is transparent and content runs to the top edge. The 28px titlebar strip holds static content only. Document windows cascade from the front one, show the file's name and proxy icon, and mark unsaved edits with the close button's dot.
- **Many commands are a grid.** Where there are more than a few commands side by side, as in toolbars, tool palettes, color and thickness choices, or a row of formats, raised buttons would be too much. Instead they're a `kit::Grid`: one flat strip ruled into cells by hairlines, where each cell is a button. Hovering a cell shows its tooltip, and a cell that's on (the tool in use, the chosen option) is filled in.
- **Every icon-only control has a tooltip** with its name and shortcut. It shows the moment the pointer is over the control, centered under it, never after a delay or at the pointer. *(Provided by `kit::Grid` and the overlay in `kit::root`; GPUI's own `.tooltip()` isn't used.)*
- **Holding ⌘ reveals shortcuts.** Held alone for a moment, ⌘ shows the shortcut of every command whose shortcut isn't already on screen, on the control that runs it, and they stay until ⌘ is let go or a key is pressed. *(Provided by `kit::Grid` and `kit::root`. A control of an app's own that hides its shortcut, like a value clicked to edit it, adds `kit::reveal_shortcut`.)*
- **Lists that scroll show a scroll thumb.** A thin neutral thumb over the list's right edge, sized to how much of the list shows, that can be dragged. *(`kit::scrollbar`.)*
- **No explanatory captions.** The UI shows controls and state, never notes explaining how things work ("Drag to move", "Enter to finish", "Saved beside the originals") and never technical details (keys, models, file paths, where a setting came from). Names belong in tooltips and menus, shortcuts on keycaps, and how things work in the doc comments agents read. Notes like these tend to come from design conversations; leave them there. Raised `kit::Button`s are kept for the few main commands in a place, like Export or Done.
- **State is unmistakable.** On, off, chosen and selected never look alike or like hover. A grid cell that's on and a chosen segment are filled with the text color, their label in the background color. A selected row has the selection fill, which hover never uses. *(Enforced: the looks live in `kit::Grid`, `kit::Segmented` and `kit::row`.)*
- **Stability:** layout never shifts as content changes. Button groups split into equal widths (`Button::grow`) instead of sizing to their labels.

## Input

- **Every command is an action.** `kit::Button` takes a GPUI action, never a closure. *(Enforced: `Button` has no click handler API.)*
- **Actions are handled app-wide, on the model**, not by a window, so they work the same from the keyboard, a click, the menu bar or an agent, with or without a window open. Actions that act on one item take an optional `id` and default to the selection. In apps with document windows, they take an optional `document` and default to the frontmost one.
- **Every action has a keyboard shortcut**, shown on its button, or in its tooltip and when ⌘ is held. *(Enforced: debug builds panic when a button's or grid cell's action has no binding.)*
- **Every action is in the menu bar**, so it can be discovered and its shortcut is listed.
- **Standard shortcuts:** ⌘Q quit, ⌘H hide, ⌘W close window *(provided by `kit::main`)*; ⌘N new item, ↩ rename item, ⌘⌫ delete item, ↑/↓ change selection, Escape dismiss an alert.
- **Typing never triggers shortcuts.** Shortcuts without a modifier (Space, letters, ↩, arrows) are bound with the context `"<App> && !TextField"`, so they turn off while a `kit::TextField` has focus. Each app has a test that checks its shortcuts against the keymap this way.
- **Times are typed the way people say them.** Any field that takes a length or a time of day reads it with `kit::TimeInput`: "5 minutes", "1:30", "1h 30m", "an hour and a half", "until 3pm", "9am tomorrow". Parsing is local and instant, and the line under the field previews what it understood as you type ("1 h 30 min, ends 12:53 PM"). The matching MCP tools take the same words, so people and agents are read identically. What the parser can't read goes to the decision model (see Principles).
- **Items are named like files.** A new item takes the lowest free number ("Stopwatch 1", then "Stopwatch 2"), so a deleted item's number is reused. Renaming is done in place: ↩ or a double-click, then Enter or clicking away saves and Escape cancels. A name that's taken, compared case-insensitively, gets the next free number: "Pasta" becomes "Pasta 2". Ids are separate from names and are never reused, so an agent's old id can't reach a newer item.

## Behavior

- **Speed first.** No work while idle: windows only redraw every frame while something is animating, such as a running stopwatch.
- **Logic is separate from UI.** App state lives in a plain model with no UI code. The window, menus, menu bar and agents all drive that model through the same actions.
- **State is saved** on every change (`kit::save`, `kit::load`), to `~/Library/Application Support/plain/<app>/`. Time is wall-clock, so anything running keeps running across quits, restarts and sleep.
- **An app's data is its own, on every device.** Data people would want everywhere, like lists, lives in the app's `store`: SQLite on each device, merged change by change (the newest edit to each field wins), and shared through a folder each device appends its own changes to, iCloud Drive by default. No server is needed, and a device that slept catches up when it wakes. What's only about this device, like what's selected, stays in `kit::save`.
- **Alerts reach you anywhere.** Something that finishes (like a timer) posts a macOS notification with the actions you'd want (Dismiss), plays the kit's chime (`kit::Sound`), and shows in the menu bar item, whether or not a window is open. Whether the chime repeats until dismissed is a setting, on by default. Notifications only appear from an installed app; under `cargo run`, GPUI skips them.
- **An original is never lost.** Edits stay separate from the file, each one undoable, until Save writes them in. The first time an app saves over a file it keeps the untouched original in its data folder, and Revert to Original puts it back. Exports and copies are written as new files beside the original, named the way Finder names copies ("photo 2.jpg"), and closing or quitting with unsaved edits asks first. Nothing is ever deleted.
- **One copy per app.** Launching an app that is already running brings it to the front. *(Provided by `kit::main`.)*
- **Open With, never the default.** An app that works on files is in Finder's Open With menu for them, and opening a file there opens it in its own window, or brings forward the window already showing it. It never makes itself the default app for a file type. *(Declared with `opens` in `[package.metadata.bundle]`, handled with `kit::on_open_files`.)*
- **Pixels stay sharp up close.** Zoomed in past one image pixel per screen pixel, each pixel is drawn as a solid square, never smoothed.

## Agents

- **Every app is its own MCP server.** `<app> mcp` speaks MCP over stdio and relays to the running app through a local socket, launching it in the background (`--background`, no window) when a tool is called. An agent and the person at the keyboard share one live state. *(Provided by `kit::main`.)*
- **Quitting sticks.** Agents list an app's tools from a copy the app saved, so an agent session starting never relaunches a quit app; only a tool call does. An app started for an agent stays out of the Dock and the app switcher until it shows a window, and leaves them again when its last window closes, unless the person opened it themselves. *(Provided by `kit::main`.)*
- **Window-only actions stay out of the tools.** Actions that only drive the window, such as starting a rename, use the `<app>_window` namespace. Agents call the underlying command (`rename`) directly.
- **Tools are generated from actions.** Each of the app's actions becomes a tool: its name in snake_case, its doc comment as the description, its fields as the input schema. So every action is agent-accessible by construction, and the doc comment on an action is written for agents. *(Enforced: there is no other way to add a tool.)*
- **Every tool returns the app's state** after the change, as reported by `kit::report_state`. `get_state` reads it without changing anything.
- **Agents look without interrupting.** The `screenshot` tool, or `<app> screenshot` from a shell, saves PNGs of the app's windows as they are right now, even when covered or on another Space, and needs no Screen Recording permission. With no window open, it captures the main window, opened out of sight just for the capture. Check UI this way. Never bring an app forward or take over the screen to look at it. *(Provided by `kit::main`.)*
- **Agents show their work, but never take the keyboard.** A window an agent opens, or one whose content an agent changes, comes to the front so the person sees it happen. It doesn't become key, so typing elsewhere carries on. *(`kit::present`.)*
- **Long actions finish before the agent hears back.** An action that starts background work (reading or writing files) registers it with `kit::finish_before_replying`, so the agent's reply shows the finished result, like the paths and sizes of exported files. If the work fails, the call fails with its error.
- **Errors are for agents to read.** An action that can't apply (such as an unknown `id`) calls `kit::reject`, and the agent gets the message instead of a silent no-op.
- **Every change is heard.** Actions are handled with `kit::handle`, which updates the model and then reports the action as an `action.performed` event (MCP's events extension): what was done, its arguments as the tool takes them, and whether the person or an agent did it. Handlers that finish later take a `kit::announcer` as they start and announce with it once they're done. Changes that arrive any other way, like edits synced from another device, call `kit::changed` so subscribed hosts read again. Apps add their own event types with `kit::event_source`, backed by a log so a host can catch up from its cursor. *(Provided by `kit::handle`; agent calls to apps that don't use it are still heard.)*
- **Widgets are written once, in A2UI.** A view of the app that hosts can show, like a list someone can tick off, is a `kit::widget`: A2UI 1.0 basic-catalog components and the data they bind to, made from a `Show<Name>` arguments struct whose doc comment describes it to agents. It becomes the `show_<name>` tool, whose result carries the A2UI messages for hosts that draw A2UI and a line of text for those that don't, and a resource hosts subscribe to so it stays live. A tap names the tool it calls, with that tool's arguments as its context, so ticking an item in a widget is exactly what an agent calling `tick` does. Icons are the kit's, through `kit::svg_icon`. *(Provided by `kit::widget`.)*
- **A tap is the person's.** A host forwarding a tap on a widget passes the A2UI action in the tool call's `_meta` (`a2ui/action`), so the change counts as the person's own: it's heard with `by: "person"`, and windows don't jump forward as they do for an agent.

## Stack

- Rust and GPUI, with one Zed revision pinned in the workspace `Cargo.toml`. Apps don't choose their own versions.
